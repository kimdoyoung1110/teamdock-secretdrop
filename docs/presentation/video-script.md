## 1부 — 소개 (약 1분 30초)

### 슬라이드 1 · 표지

안녕하세요. 암호와인증 SSO 실습 과제를 발표하겠습니다.
저는 Keycloak으로 두 개의 웹 서비스에 SSO를 적용했습니다. 서비스 이름은 TeamDock과 SecretDrop이고, 이 중 SecretDrop은 암호학 기술이 들어간 시크릿 공유 서비스입니다.

### 슬라이드 2 · 문제와 해결

먼저 왜 이 서비스를 만들었는지 말씀드리겠습니다.
팀 프로젝트를 하다 보면 ".env 파일 좀 보내줘"라는 말을 자주 합니다. 그러면 API 키나 DB 주소, 공용 계정 비밀번호가 카카오톡으로 오갑니다. 문제는 한 번 보낸 값이 채팅방에 평문으로 계속 남는다는 점입니다. 팀을 나간 사람도 다시 볼 수 있고, 누가 언제 봤는지도 알 수 없습니다.

그래서 두 가지 서비스를 만들었습니다. 서비스 A인 TeamDock은 팀을 만들고 멤버를 관리하는 팀 워크스페이스입니다. 서비스 B인 SecretDrop은 비밀값을 암호화된 링크로 공유하고, 열면 사라지게 하는 서비스입니다.

서비스가 둘로 나뉜 데는 이유가 있습니다. 팀 관리와 비밀값 보관은 책임이 다른 서비스입니다. 그런데 "이 시크릿은 우리 팀만 볼 수 있다"가 되려면 두 서비스가 같은 사용자를 알아야 합니다. 그래서 계정을 Keycloak 하나에 두는 SSO가 필요합니다.

### 슬라이드 3 · 시스템 구성

시스템 아키텍처입니다. 네 개의 계층으로 나누어 설계했습니다.
왼쪽이 클라이언트 계층인 브라우저입니다. 가운데가 애플리케이션 계층으로, TeamDock과 SecretDrop이 각각 독립된 Next.js 서비스로 Vercel에 배포되어 있습니다. 아래가 인증 계층으로, Keycloak이 Cloud Run 컨테이너로 돌아갑니다. 오른쪽이 데이터 계층인 Neon PostgreSQL입니다.

이 구조에는 세 가지 설계 원칙이 있습니다.

첫째, 인증 책임을 Keycloak 한 곳에 모았습니다. 두 서비스는 비밀번호를 받지도, 저장하지도 않습니다. 각 서비스 안의 Auth.js가 OIDC 클라이언트 역할을 하고, Keycloak이 서명한 토큰을 검증해서 사용자를 확인합니다.

둘째, 서비스를 서로 격리했습니다. 데이터베이스도 서비스마다 따로이고, 세션 쿠키도 따로입니다. 다른 서비스의 DB에는 직접 접근하지 않습니다. SecretDrop이 팀 소속을 알아야 할 때는, 가운데 세로선처럼 사용자의 Access Token을 들고 TeamDock의 API를 호출합니다.

셋째, 평문은 브라우저 밖으로 나가지 않습니다. 왼쪽 아래 WebCrypto가 브라우저 안에서 암호화를 끝내고, 암호문만 SecretDrop으로 올라갑니다. 그래서 Vercel에도 Neon에도 평문과 키가 없습니다.

통신 경로는 선의 종류로 구분했습니다. 파란 선은 브라우저를 거치는 경로로, 페이지 요청과 로그인 리다이렉트입니다. 회색 선은 브라우저를 거치지 않는 서버 간 경로로, 토큰 교환과 Back-Channel Logout이 여기로 다닙니다. 점선은 배포 경로입니다. main 브랜치에 push하면 Vercel이 두 서비스를 자동 배포하고, Keycloak은 컨테이너 이미지를 올려 Cloud Run에 배포합니다.

마지막으로 상태가 어디에 있는지입니다. 두 서비스는 세션을 암호화된 쿠키에 담아 서버에 상태를 두지 않습니다. 그래서 서버리스 환경에 그대로 올릴 수 있었습니다. 반대로 Keycloak은 세션을 DB에 저장하기 때문에, 컨테이너가 잠들었다 깨어나도 로그인 상태가 유지됩니다.

### 슬라이드 4 · 구현 환경

기술 선택에 대해 한 가지만 말씀드리겠습니다.
React만 쓰지 않고 Next.js를 쓴 이유는 서버 코드가 반드시 필요했기 때문입니다. 토큰을 교환할 때 Client Secret이 필요한데, 이 값은 브라우저 코드에 넣을 수 없습니다. 또 로그아웃 알림은 Keycloak이 서버로 직접 보내는 요청이라, 받을 서버가 있어야 합니다.

### 슬라이드 5 · Keycloak 설정

Keycloak에는 realm 하나에 클라이언트 두 개를 등록했습니다. 두 클라이언트 모두 Client Secret을 쓰는 Confidential Client이고, PKCE S256을 필수로 설정했습니다.
오른쪽은 실제 관리자 콘솔 화면입니다. 위쪽이 Redirect URI, 아래쪽이 Back-Channel Logout 주소입니다.
이 설정은 전부 JSON 파일로 레포에 들어 있어서, docker compose 한 번으로 똑같이 재현됩니다.

### 슬라이드 6, 7 · 서비스 화면

[6장] TeamDock의 팀 화면입니다. 팀을 만들면 만든 사람이 Owner가 되고, 초대 링크를 받은 사람은 로그인 후 Member로 합류합니다.
[7장] SecretDrop입니다. 내용을 쓰고 공개 범위와 만료 시간을 정하면 공유 링크가 만들어집니다.
이제 실제로 동작하는 모습을 보여드리겠습니다.

## 3부 — 원리와 암호학 (약 2분 30초)

### 슬라이드 13 · SSO 동작 원리

SSO가 어떻게 동작하는지 정리하겠습니다.
1번부터 7번까지가 서비스 A 로그인입니다. 사용자가 A에 접속하면 A는 브라우저를 Keycloak으로 보냅니다. 사용자가 로그인하면 Keycloak은 자기 세션 쿠키를 브라우저에 심고, 일회용 code를 붙여 A로 돌려보냅니다. A의 서버는 이 code를 Client Secret과 함께 Keycloak에 보내 토큰으로 바꾸고, 자기 세션 쿠키를 발급합니다.

8번부터가 SSO입니다. 사용자가 B에 접속하면 B도 브라우저를 Keycloak으로 보냅니다. 그런데 이번에는 브라우저에 Keycloak 세션 쿠키가 이미 있습니다. 그래서 Keycloak은 로그인 화면 없이 바로 code를 발급합니다.

핵심은 세션이 두 층이라는 점입니다. A와 B는 쿠키를 공유하지 않습니다. 공유되는 것은 Keycloak 세션 하나뿐이고, 각 서비스는 그것을 근거로 자기 세션을 따로 만듭니다.

### 슬라이드 14 · 암호학 ① E2E 암호화

다음은 암호학입니다. SecretDrop은 서버가 내용을 볼 수 없는 구조입니다.
작성자의 브라우저가 무작위 256비트 키를 만들고, AES-256-GCM으로 암호화합니다. 서버에는 암호문과 iv만 보냅니다. 키는 링크의 샵 뒤에만 있습니다.
열람자의 브라우저는 암호문을 받아서 링크의 키로 복호화합니다. 그래서 서버와 DB가 통째로 유출되어도 평문은 알 수 없습니다.
비밀번호를 걸면 PBKDF2-SHA-256을 60만 번 반복해 키를 만들고, 그 키로 한 겹 더 암호화합니다.

### 슬라이드 15 · 암호학 ② 증거

실제 DB를 조회한 결과입니다. 위쪽은 열람 전이고 암호문만 있습니다. 아래쪽은 열람 후이고 암호문이 지워졌습니다.
DB 전체와 서버 로그에서 키, 평문, 비밀번호를 검색했을 때 결과는 0건이었습니다.

### 슬라이드 16 · 암호학 ③ 인증 계층

인증 흐름 자체에도 암호 기술이 들어 있습니다.
첫째, PKCE입니다. 앱이 무작위 값을 만들고 그 SHA-256 해시만 먼저 보냅니다. 토큰을 받을 때 원본 값을 보내서, 중간에 code를 가로채도 토큰을 받을 수 없게 합니다.
둘째, JWT 서명입니다. Keycloak이 개인키로 토큰에 서명하고, 서비스는 공개키로 검증합니다. 위조한 토큰으로 API를 호출하면 401로 거절됩니다.
셋째, 세션 쿠키도 암호화된 JWT로 저장하고, 페이지 스크립트가 읽지 못하게 했습니다.

## 4부 — 마무리 (약 1분)

### 슬라이드 17 · 트러블슈팅

구현하면서 겪은 문제 중 두 가지만 말씀드리겠습니다.
첫째는 쿠키 충돌입니다. 쿠키는 포트를 구분하지 않아서, localhost의 9000번과 9001번 서비스가 서로의 세션 쿠키를 덮어썼습니다. 서비스마다 쿠키 이름에 접두어를 붙여 해결했습니다.
둘째는 링크 미리보기입니다. 페이지를 여는 것만으로 시크릿을 파기하면, 메신저의 미리보기 봇이 먼저 열어 버립니다. 그래서 버튼을 눌러야만 암호문을 내주도록 했습니다.

### 슬라이드 18 · 소감

[본인 말로 고쳐서 읽는다. 아래는 초안]
이번 과제에서 가장 크게 배운 점은, SSO가 쿠키를 공유하는 방식이 아니라는 것입니다. 직접 요청 흐름을 찍어 보고 나서야 Keycloak 세션과 앱 세션이 따로라는 구조가 이해됐습니다.
그리고 로그인보다 로그아웃이 더 어려웠습니다. 강의 예제의 한계를 직접 겪고 Back-Channel Logout으로 풀어 본 것이 가장 많이 남았습니다.
암호화에서는 알고리즘보다 키를 어디에 두느냐가 더 중요하다는 것을 느꼈습니다.

### 슬라이드 19 · 링크

소스코드와 배포 주소는 마지막 장에 있습니다. README를 보시면 docker compose로 로컬에서도 바로 실행할 수 있습니다.
이상으로 발표를 마치겠습니다. 감사합니다.
